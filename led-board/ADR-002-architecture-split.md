# ADR-002: 機能肥大化への対策 — 分割 / プラグイン / HTML-only

## ステータス
提案

## コンテキスト

LED Board は元々「外部から HTTP POST でメッセージを受け取り、LED 風にスクロール表示する」
だけのシンプルな仕組みだった。しかし以下の機能が追加され、サーバー (dev-server.ts) が
1 ファイル 500 行を超えるモノリスになりつつある：

| 機能 | 種別 | 依存 |
|---|---|---|
| メッセージ表示 (API) | コア | なし |
| SSE プッシュ通知 | コア | なし |
| CSV ログ | コア | ファイルI/O |
| Supabase Realtime | 外部連携 | Supabase SDK |
| RSS ニュース | プラグイン的 | Yahoo RSS |
| 音楽 fingerprint (LISTEN) | プラグイン的 | Rust WASM, ffmpeg |
| カラーピッカー / サイズ / 光彩 / 行列 / 速度 | UI | ブラウザのみ |

懸念：
- 1 台の Raspberry Pi / サーバーで全部動かす必要はない
- LISTEN 機能は WASM + ブラウザ画面共有 + サーバーfingerprint と複雑
- RSS ニュースもサーバー定期 fetch + クライアントUI連携で結合度が高い
- 「表示だけ」の軽量クライアントが欲しい場合、今の構成ではサーバー必須

## 決定

**即座の分割は行わず、以下の方針で進める：**

1. `led-board/` は「フル機能版（サーバー必要）」として現状維持
2. 別ディレクトリ `led-board-lite/` に **HTML-only 超軽量版** を作成
   - サーバー不要、静的な HTML 1 ファイル
   - URL クエリパラメータ or localStorage でメッセージを受け取る
   - 表示機能のみ（カスタマイズは CSS 変数 or URL パラメータ）
3. プラグイン化は**次フェーズ**で検討（ADR-003 に持ち越し）

## 議論

### 選択肢 A: 現状維持（モノリス）

**メリット**
- 結合済みで動作確認済み、すぐ動く
- 1 プロセスで管理容易

**デメリット**
- 機能追加ごとに dev-server.ts が肥大化
- LISTEN 機能が落ちると表示も止まる（単一障害点）
- 軽量クライアントが欲しい場合にサーバー全体が必要

### 選択肢 B: プラグインアーキテクチャ（採用見送り）

各機能を独立したプラグインとして切り出し、コアは最小限に。

```
led-board/
├── core/           # 表示 + SSE 配信のみ
├── plugins/
│   ├── news/       # RSS 購読 → コアに POST
│   ├── listen/     # WASM fingerprint → コアに POST
│   └── supabase/   # Supabase Realtime → コアに POST
└── index.html
```

**メリット**
- 機能の追加・削除が容易
- 各プラグインが独立して開発・停止可能
- コアのテストが容易

**デメリット**
- 現状から移行するコストに対して即時メリットが薄い
- プラグイン間通信の設計（IPC / HTTP / 標準入力）が必要
- 現時点でプラグイン候補は NEWS と LISTEN の 2 つだけ
- 過度な抽象化になるリスク

### 選択肢 C: HTML-only Lite 版を作成（採用）

サーバー不要、ブラウザだけで動く LED 表示板。

```
led-board-lite/
└── index.html      # 1 ファイル完結
```

メッセージの受け渡し方法：

| 方法 | 使い方 |
|---|---|
| URL hash | `file:///.../index.html#Hello` |
| URL query | `?msg=Hello` |
| localStorage | 別タブで `localStorage.setItem("msg","Hello")` → `storage` イベントで受信 |
| 手動入力 | テキストボックスに入力 |

**メリット**
- サーバー不要、どこでも開ける
- GitHub Pages / Vercel / Netlify に置くだけ
- コード量が極小（〜200行）
- フル版と併用可能

**デメリット**
- NEWS / LISTEN 機能なし
- 履歴ログなし
- SSE プッシュなし（localStorage ポーリングで代替可）

### 選択肢 D: マイクロサービス（採用見送り）

各機能を別ポート・別プロセスで起動。

**メリット**
- 完全な分離、言語も自由

**デメリット**
- 運用複雑
- オーバーエンジニアリング

## 結果

### メリット
- フル版と Lite 版を用途で使い分けられる
- Lite 版はコードが短く、改造も容易
- 新機能のプロトタイプを Lite 版で先に試せる

### デメリット
- メンテナンス対象が 2 つになる
- 表示ロジックに差分が生じる可能性（bug fix を二重適用）
- フル版の肥大化自体は解決しない

### 対応策
- Lite 版はコア表示ロジックのみに徹する（カスタマイズは CSS 変数 + URL param）
- フル版の表示ロジックと Lite 版の表示ロジックは同期を保つ（コピーではなく参照）
- 次フェーズでプラグイン化（ADR-003）を再検討

## 実装計画

| Phase | 内容 | 成果物 |
|---|---|---|
| 1 | フル版の現状維持 + ADR 文書化 | この ADR |
| 2 | `led-board-lite/index.html` 作成 | サーバー不要の超軽量版 |
| 3 | フル版のプラグイン化検討（ADR-003） | 設計書 |
